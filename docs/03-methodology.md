# 03 — Methodology & Mathematics

This document describes the three machine-learning / quantitative components and
the mathematics behind them. It is the technical core of the thesis and
conference paper.

## 1. Problem formulation

Given a Uniswap v3 liquidity pool, we seek to answer three questions:

1. **Liquidity dynamics** — how likely is the pool to experience a liquidity
   drain (providers withdrawing capital) in the near term?
2. **Price impact** — how much will a trade of a given size move the pool's
   price?
3. **Price outlook** — what is the next-day price of the underlying asset, with
   a calibrated uncertainty band?

The answers feed an **algorithmic market-making policy** (see
[`04-market-making.md`](04-market-making.md)).

## 3. Component 1 — Liquidity-drain prediction

### 3.1 Feature engineering

`backend/app/ml/features.py` defines a **fixed-order** 8-feature vector shared by
the training script and the live predictor:

| # | Feature | Meaning |
| --- | --- | --- |
| 1 | `liquidity_change_pct_1m` | Relative liquidity change vs. 1 min ago |
| 2 | `liquidity_change_pct_5m` | Relative liquidity change vs. 5 min ago |
| 3 | `liquidity_change_pct_15m` | Relative liquidity change vs. 15 min ago |
| 4 | `reference_impact_pct` | Price impact of a $100k reference trade |
| 5 | `pending_swaps` | Number of pending mempool swaps |
| 6 | `fee_tier` | Pool fee tier (hundredths of a bip) |
| 7 | `log_liquidity` | `log10(liquidity)` |
| 8 | `price_volatility_5m` | Std. dev. of period-over-period returns |

The monitor (`tasks/monitor.py`) computes these from a rolling snapshot history:
`_pct_change` finds the baseline snapshot nearest the requested horizon, and
`_volatility` computes the population standard deviation of price returns.

### 3.2 Model

`backend/app/ml/model.py` wraps an `XGBClassifier`:

```
n_estimators=200, max_depth=4, learning_rate=0.05,
subsample=0.8, colsample_bytree=0.8, eval_metric="logloss"
```

The output is the **positive-class (drain) probability** `p ∈ [0, 1]`.

Training data is synthetic (20,000 rows) generated by `scripts/train_model.py`
under a logistic risk model driven by negative liquidity changes, reference
impact, pending swaps and volatility.

### 3.3 Alert levels

`DrainPredictor._alert_level` maps the probability to a discrete level:

| Probability | Level |
| --- | --- |
| `p ≥ 0.8` | CRITICAL |
| `0.6 ≤ p < 0.8` | HIGH |
| `0.3 ≤ p < 0.6` | MEDIUM |
| `p < 0.3` | LOW |

### 3.4 Heuristic fallback

When no trained model exists, `DrainPredictor._heuristic` computes a transparent
additive score, each bucket contributing a fixed weight, capped at `0.95`:

| Signal | Condition | Weight |
| --- | --- | --- |
| Liquidity change | `≤ -0.25` / `≤ -0.15` / `≤ -0.05` | `+0.50` / `+0.35` / `+0.15` |
| Reference impact | `≥ 10%` / `≥ 5%` / `≥ 2%` | `+0.30` / `+0.20` / `+0.10` |
| Pending swaps | `≥ 20` / `≥ 5` | `+0.10` / `+0.05` |
| Volatility | `≥ 0.05` | `+0.05` |

This keeps the pipeline **transparent and runnable with no model**, an important
property for reproducibility and auditability in a research setting.

## 4. Component 2 — Price-impact mathematics (Uniswap v3)

`backend/app/services/price_impact.py` reproduces the exact integer arithmetic of
the Uniswap v3 core contracts, so results are overflow-safe and unit-testable
without a node.

### 4.1 Concentrated-liquidity invariant

Uniswap v3 keeps liquidity `L = sqrt(x·y)` constant within a tick range, where
`x` and `y` are the reserves of token0 and token1, and the price is `P = y / x`.
On-chain state stores the **square root** of the price scaled by `2^96`
(Q64.96 fixed point):

```
sqrtPriceX96 = sqrt(P) · 2^96
```

From `x·y = L²` and `P = y/x` we get the useful identities:

```
x = L / sqrt(P)        y = L · sqrt(P)        sqrt(P) = y / L = L / x
```

### 4.2 Exact-input swap

For an exact-input swap of token0 → token1 (price moves down), after adding
`amount0_in` units the new reserve is `x' = x + dx`, and because `x'·y' = L²`:

```
sqrtP'_X96 = sqrtP_X96 · L · Q96 / (L · Q96 + dx · sqrtP_X96)
```

For token1 → token0 (price moves up):

```
sqrtP'_X96 = sqrtP_X96 + (dy · Q96) / L
```

The output amounts are then derived exactly:

```
dx = L · Q96 · (sp_new − sp_old) / (sp_old · sp_new)   (token0 out)
dy = L · (sp_old − sp_new) / Q96                       (token1 out)
```

### 4.3 Price impact

`PriceImpactService.quote` simulates an exact-input swap and reports:

```
price_impact_pct = (price_after − price_before) / price_before · 100
```

A reference-trade helper `quote_usd` sizes a ~$100k trade in the non-stable
token so the reference impact is meaningful regardless of the quote currency.
This reference impact feeds feature `#4` of the drain classifier.

### 4.4 Event-stream inference (`services/liquidity_predictor.py`)

For each live Swap/Burn event, the predictor estimates a utilization ratio and a
linear slippage approximation (or uses a `.pkl` model when present):

```
utilization = swap_volume / reserve_depth
predicted_price_impact = min(utilization · 100, 100)
gas_pressure = max(0, (gas_gwei − 30) / 300)
drain = utilization · 100 · 0.6 + gas_pressure · 30   (+5 if Burn)
```

Risk level: `max(drain, impact) ≥ 20 → High; ≥ 8 → Medium; else Low`.

## 5. Component 3 — Quantile price forecasting

### 5.1 Features and target

`crypto-forecast/config.py` defines 10 features, and `features.py` constructs the
target with a `shift(-1)` (today's row predicts tomorrow):

```
features = [open, high, low, close, volume,
            sp500_close, dxy, gold, treasury_10y, gpr]
target   = close.shift(-1)        # next-day close (regression)
```

Traditional-market series (S&P 500, DXY, gold, Treasury) are forward-filled onto
the crypto's 7-day calendar to close weekend/holiday gaps.

### 5.2 Leakage control

`model.py` splits chronologically (80/20, **no shuffle**), so the model is only
ever evaluated on strictly future data:

```python
cut = int(len(df) * split)
train, test = df.iloc[:cut], df.iloc[cut:]
```

### 5.3 Quantile regression

The model is an `XGBRegressor` with the multi-quantile objective:

```
objective="reg:quantileerror", quantile_alpha=[0.025, 0.5, 0.975],
n_estimators=300, max_depth=5, learning_rate=0.05,
subsample=0.9, colsample_bytree=0.9, tree_method="hist"
```

- The **median** (0.5) is the headline point forecast.
- The **2.5th / 97.5th percentiles** give a 95% predictive interval.

### 5.4 Uncertainty & confidence

`predict_with_uncertainty` reports an interval `ŷ ± 1.96·RMSE` and a confidence
score that reflects how tight the band is relative to the price level:

```
confidence = 100 · (1 − 1.96 · RMSE / ŷ)
```

If no RMSE is available, the quantile bounds are used directly.

### 5.5 Evaluation

| Task | Metrics |
| --- | --- |
| Regression (forecast) | MAE, RMSE, R² |
| Classification (drain) | positive-class probability → alert level |

The forecast registry persists each model (`{TICKER}_xgb.json`) plus metadata
(`{TICKER}_meta.json`: features, metrics) so the serving layer always reads
feature order from the trained artifact.
